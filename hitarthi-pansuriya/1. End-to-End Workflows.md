Detailed Step List (Mode A)
Trigger: User clicks "Start Batch Run" on the Batch Run Screen.

Dataset Validation: System loads the dataset records. If records are missing required fields (id, question, category, is_trap, key_false_claim, correct_behaviour, reference_fact), the system halts with a validation error.

Execution Loop: System iterates sequentially or concurrently through each combination: Question×PromptVersion(V1,V2,V3)×Model(ModelA,ModelB).

Model Call: For each combination:
a. System constructs the payload using the specified prompt version and question.
b. System sends the payload to the specified model API and measures latency in milliseconds.

Output Validation & JSON Guardrail:
a. If API times out or fails: System retries up to 2 times. If it still fails, logs API_ERROR and moves to the next item.
b. If response is received: System validates if it adheres to the schema {"verdict", "problematic_claims", "answer"}.
c. If JSON parsing fails or schema mismatch occurs: System sends a JSON-repair prompt (1 retry). If repair fails, stores result as parsed_json: null with INVALID_OUTPUT flag.

Judge Evaluation:
a. System passes the raw question, dataset ground truth (is_trap, key_false_claim, reference_fact), and parsed model response to the Judge Model.
b. Judge Model returns {"label", "reason", "invented_span"}.
c. If Judge Model output is unparseable: System retries 1 time. On second failure, flags JUDGE_ERROR.

Storage & Metric Update: System stores the full execution result record in memory/database and increments the UI progress bar and real-time metric counters.

Completion: Once all combinations finish, the system computes overall dataset metrics and unlocks the Results Dashboard and Side-by-Side Comparison screens.

Detailed Step List (Mode B)
Trigger: User enters a new question on the Live Test screen (or clicks "Re-run Question" in the Prompt Editor after modifying prompt text).

Input Guardrail Check:
a. Check length: If empty or >500 characters, flag input error.
b. Pre-filter evaluation (or model-based check): If off-topic/malicious, flag off-topic error.

Parallel Dispatch: System triggers execution for all 3 prompt versions (V1, V2, V3) on the chosen model(s) simultaneously.

Response Processing & Guardrail Enforcement:
a. For each prompt output, validate JSON formatting. If invalid, attempt 1 repair retry.
b. If verdict returns OUT_OF_SCOPE, handle according to guardrail policies (display out-of-scope notice without calling Judge).

Live Evaluation: For valid outputs, pass response data to the Judge Model to obtain {"label", "reason", "invented_span"} in real time.

Side-by-Side Render: Render 3 parallel cards (V1, V2, V3) displaying:

Prompt Version & Model Name

Status Badges (Verdict, Judge Label)

Problematic Claims Extracted (if any)

Final Answer Text

Execution Latency (ms)

Timestamp

History Logging: Append the execution event with a timestamp to the persistent Timestamped Prompt History log.

2. Guardrail Matrix
Situation	How it is Detected	What the System Does	What the User Sees
Invalid or non-JSON model output	JSON parser fails or output lacks required keys (verdict, problematic_claims, answer).	System automatically triggers 1 retry with a dedicated JSON-repair system prompt. If retry fails, stores parsed_json: null and skips Judge call.	Warning badge "INVALID_OUTPUT" on card; display raw text with warning: "Model output was not valid JSON. Raw output retained for audit."
Empty or oversized input	String length check on submission (len == 0 or len > 500 characters).	Submission is blocked before sending API requests.	Inline error message under input box: "Input must be between 1 and 500 characters."
Off-topic input	Pre-execution classifier or model returns verdict: "OUT_OF_SCOPE".	Halts further processing (bypasses Judge Model evaluation).	Display Guardrail Alert Card: "Query flagged as OUT_OF_SCOPE. The prompt successfully rejected unhandled domain input."
Model verdict: OUT_OF_SCOPE	Parsed model JSON contains "verdict": "OUT_OF_SCOPE".	System flags item as correctly/incorrectly scoped based on question category; skips Judge claim extraction.	Yellow badge "OUT_OF_SCOPE" rendered on the response card alongside the model's explanation.
Model refusal on a TRAP question	is_trap: true AND (model verdict is FALSE_PREMISE or UNVERIFIABLE OR response text explicitly declines false premise).	Judge labels response as CORRECT_DEFENSE. System logs successful trap mitigation.	Green badge "CORRECT_DEFENSE" with explanation: "Model correctly identified and rejected the trap."
Model refusal on a CONTROL question	is_trap: false AND (model verdict is FALSE_PREMISE or UNVERIFIABLE or model declines to answer).	Judge labels response as OVER_REFUSAL. System increments Over-Refusal metric.	Red/Orange badge "OVER_REFUSAL" with explanation: "Model refused a valid, factual control question."
API error or timeout	HTTP status ≥400, network connection dropped, or call exceeds 15,000 ms timeout.	Retries API call up to 2 times exponentially. If all retries fail, logs system error.	Error state on UI card: "API Error / Timeout after 2 retries. Click to retry manually." button provided.
Judge Model returning invalid output	JSON parser fails on Judge response or missing required fields (label, reason).	System retries Judge call 1 time. If it fails again, logs JUDGE_ERROR and falls back to unlabelled state.	Badge "JUDGE_ERROR" displayed in place of judge label, with raw judge output visible in expandable debug tray.
